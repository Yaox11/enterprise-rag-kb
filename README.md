# 企业知识库智能问答 Agent（RAG）

一个可运行、可演示、可评测的 RAG 项目：混合检索 + Cross-Encoder 重排 + 带引用生成。

## 语料

| 目录 | 内容 | 用途 |
| --- | --- | --- |
| `corpus/` | 7 篇自造的企业制度文档 | 早期实验，`stage0-5` 的评测集基于它 |
| `corpus_real/` | **264 篇 Dify 官方中文文档**，约 150 万字符、6143 个片段 | 真实语料演示 |

`CORPUS_SOURCES.md` 记录了每篇的原始链接。切换语料只需在 `.env` 里改：

```
RAG_CORPUS_DIR=corpus_real
```

语料有变化时 embedding 会自动重算并落盘缓存到 `work/emb_cache/`。实测：
全量 264 篇首次建库约 2 分钟，之后启动约 30 秒，`/reindex` 约 12 秒。

> 语料版权归 Dify 所有，仅用于本地学习与评测。

## 快速开始

1. 确认 `.env` 里有 `LLM_API_KEY`：

```
LLM_API_KEY=sk-xxxxx
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-chat
```

2. 一键启动两个服务：

```
outputs\rag-kb-agent\start_demo.cmd
```

3. 浏览器打开 http://127.0.0.1:8501 。模型首次加载约 15 秒，侧栏显示「API 未启动」时稍等再刷新。

手动启动也可以：

```
cd outputs\rag-kb-agent
python -m uvicorn app.api:app --host 127.0.0.1 --port 8000
python -m streamlit run app\ui.py --server.port 8501
```

## API

```
GET  /health
POST /ask   {"question": "...", "top_k": 3}
POST /reindex        重建索引（改完 corpus 后调用，无需重启）
POST /refresh        增量更新（只处理新增 / 修改 / 删除的文件）
```

返回示例：

```json
{
  "answer": "出差去上海，酒店一晚最多能报600元。[1]",
  "citations": [
    {"id": 1, "source": "01_差旅报销制度.md#1", "snippet": "## 二、住宿标准 ...", "score": 0.8159}
  ],
  "latency_ms": 2821,
  "model": "deepseek-chat",
  "cached": false
}
```

错误约定：参数不合法返回 422；未配置 key 返回 503；上游模型异常返回 502。

### 文档更新

索引在服务启动时构建并常驻内存。修改 `corpus/` 下的文件后，有两种方式让它生效：

1. 界面左侧点「更新所有文档」（内部调用 `POST /reindex`，2-3 秒）；
2. 或者重启 API 进程。

侧栏会显示当前文档数、片段数和索引时间，可以用来确认新内容是否已被收录。

## 真实语料评测（`corpus_real/`）

`eval_set_real.json` + `stage6_eval_real.py`。题目由 LLM 基于真实片段生成，再经过两道过滤：

1. **去重**：同一问法只保留一条；
2. **剔除通用题**：答案关键词在超过 2 篇文档里出现的题（比如「API 密钥怎么认证」）gold 文档是随机的，直接删。

没有用「必须召回」来筛题——那只会留下容易的题，评测会失真。

| 类别 | 数量 | 指标 |
| --- | --- | --- |
| 单跳 | 26 | Hit@1 **0.81** / Hit@3 0.85 / MRR 0.83 |
| 多跳 | 5 | Coverage@5 0.70 / AllHit@5 3/5 |
| 无答案 | 10 | top1 重排分最高 0.096，有答案题最低 0.587 |

**一个重要发现**：6036 个片段的规模下，重排分数能把「有答案」和「没答案」分开
（0.096 vs 0.587），阈值取 0.3 左右即可。合成语料上这两类分数是重叠的，
说明**拒答阈值不能拍脑袋，必须按语料规模和分布重新标定**。

```powershell
outputs\run.cmd outputs\rag-kb-agent\stage6_eval_real.py
```

### 端到端生成（`stage7_eval_gen.py`）

| 指标 | 值 |
| --- | --- |
| 答对率（LLM 裁判） | 20/26 = 77% |
| 引用率 | 26/26 = 100% |
| 误拒率 | 3/26 = 12% |
| 无答案拒答率 | 10/10 = 100% |
| 延迟 | 检索 3730 ms / 生成 945 ms / 裁判 792 ms |

**77% 是严格下界。** 逐条人工复核 6 条失败：

- 2 条是检索没给到关键片段（接口路径、操作入口），属于召回问题；
- 2 条是真错/答不全（默认输出字段、可设错误处理的节点列举）；
- 1 条是题目本身有歧义（问「多久更新」但文档只给了「定期」）；
- 1 条是裁判过严（回答给了接口名但没给 HTTP 路径）。

人工校准后大致在 81% 左右。这说明 **LLM 当裁判有噪声，必须人工抽检**，
也是面试里可以主动讲的一个点。

### 置信度门控（拒答阈值）

服务在调用模型前先看最高重排分，低于 `REFUSAL_THRESHOLD` 直接短路拒答。阈值可通过 `.env` 调整。

标定依据（`corpus_real` 实测）：

| 类别 | 最高分 | 最低分 |
| --- | --- | --- |
| 无答案题（10） | 0.096 | — |
| 有答案题（26） | — | 0.321 |

安全区间是 0.096 ~ 0.321，取中点附近 **0.2**：误拒 0/26，拦截 10/10。

效果：拒答路径约 3.8 s（只检索），正常路径约 5.2 s（检索 + 生成），省掉一次模型调用，
同时避免模型在低相关上下文上硬答。

### 多跳查询分解（`stage8_multihop_real.py`）

| 策略 | Coverage@5 | AllHit@5 | AllHit@3 |
| --- | --- | --- | --- |
| 单查询（基线） | 0.69 | **5/8** | **3/8** |
| 分解 + 配额合并 | 0.62 | 3/8 | 2/8 |
| 分解 + 原问题重排 | 0.69 | 4/8 | 3/8 |
| 分解 + 子问题取最高分 | **0.75** | **5/8** | **3/8** |

**结论：没有净收益。** 合成语料上 7/8 → 8/8 的那套方法，换到 264 篇真实文档后不再成立。

原因有三条：

1. **子问题改写会丢术语。** 「If-Else 节点解决什么问题」的正确文档只排第 3，第 1 名是一篇快速入门；
   「知识库内容维护」甚至没召回目标文档。
2. **合并不稳。** 配额合并每个子问题只保底取一个片段，排第 3 的正确答案会被漏掉。
3. **复合问题重排不可靠。** 用原问题给候选重新打分，模型对「分别」这种并列结构判断很差。

成本还涨了约 3 倍（每个子问题都要跑一次检索 + 重排）。

所以主链路仍然用单查询，分解只作为实验代码保留。**这个负结果本身值得写进面试话术**：
在合成数据上有效的优化，必须在真实语料上复测。

### 权限过滤

每篇文档按文件名关键词分配「部门 + 密级」（`acl_for()`），检索时**在检索阶段**过滤：

- 向量库：Chroma `where` 条件（`level=0` 或「同部门且密级足够」）；
- BM25：先算全量分数，再把不可见片段置为极小值；
- 答案缓存键带上 `dept/clearance`，否则不同部门会命中同一份缓存，等于越权。

实测：

| 用户 | 提问「降级订阅什么时候生效」 |
| --- | --- |
| 研发 / 内部（1） | 拒答，最高分 0.005 |
| 财务 / 机密（2） | 正常回答，最高分 0.677 |

### 增量索引

`POST /refresh` 按「文件名 + 大小 + mtime」比对变更，只对新增/修改的文件重算 embedding，
向量库用 `delete(where={"file": ...})` 精确删除，BM25 复用已缓存的分词结果。

| 操作 | 耗时 | 结果 |
| --- | --- | --- |
| 新增一篇 | 705 ms | chunks 6036 → 6037，问题可答 |
| 修改一篇 | 625 ms | chunks 6037 → 6038，新事实可答 |
| 删除一篇 | 544 ms | chunks 回到 6036，问题重新拒答 |

对比全量重建：有 embedding 缓存约 6 秒，无缓存要数分钟。

## 已知限制

- CPU 推理，单次 3~5 s，重排是主要开销；生产应上 GPU 或换更小模型。
- 拒答阈值 0.2 是按 `corpus_real` 标定的，换语料必须重新统计分数分布。
- 26 道单跳题样本偏小，指标有统计误差；gold 是文档级，没细到片段级。
- 引用只保证格式出现，尚未验证 `[n]` 与陈述是否真的对应。
